## 一、这个插件是什么

### 1.1 定位与命名

- **插件全名**：四象限待办——昔涟帮你处理待办事项
- **简称**：四象限待办
- **工程 id**：`quadrant-todo`（工具前缀 `quadrant-todo_*`）

用户把"后面要做的事"告诉昔涟，她按**重要 × 紧急**四象限整理成彩色清单：重要紧急（红）、重要不紧急（绿）、不重要紧急（黄）、不重要不紧急（蓝），随时间自动滑动优先级、自动提醒、自动结算完成状态；桌面独立窗口提供待办全景（四象限 / 日历 / 已完成列表三种形态）。

### 1.2 解决什么问题

| 现状 | 问题 | 本插件 |
|---|---|---|
| 内建 `update_todo` 是模型自维护的会话级执行笔记本 | 会话结束就没了，不是给用户的长期待办 | 独立持久数据层，登记一次长期跟着你 |
| 待办优先级靠人脑盯 | 人会忘，快到期的事没感知 | 72h 自动滑红、24h 自动提醒（代码结算，不靠模型自觉） |
| 过期任务死在列表里或被悄悄遗忘 | 没人处理也没交代 | 到点自动转"默认完成"，亮暗灰区分"你完成的"和"到点默认完成的" |
| 待办散落在对话里，缺全景 | 想纵览得翻聊天记录 | 独立窗口三形态：四象限 / 日历 / 已完成列表 |
| 手机上想记一笔得坐到电脑前 | 移动端空白 | QQ 私聊口述即登记（功能四，二期打磨；架构上工具天然可用） |

### 1.3 功能清单与分期

| 编号 | 功能 | 内容 | 分期 |
|---|---|---|---|
| 一 | 四象限待办 | 对话登记（四属性）、双保险校验、象限滑动、主动提醒、完成状态、修改/删除/反悔 | **一期** |
| 二 | 长时限大目标辅助拆解 | 大目标分裂为精确时限小目标，小目标从属大目标、不重新判断分类 | 二期 |
| 三 | 独立 UI（三形态） | 四象限视图 / 日历视图 / 已完成列表，切换按钮切换 | **一期** |
| 四 | QQ 通道使用 | 通过已配置的 QQ 私聊口述使用上述全部对话能力；手机无 UI 页面 | 二期打磨（工具可用性为架构自带） |

**一期 = 功能一 + 功能三，即本插件的最低实现形态**；功能二、四为二期增量，本文档只预埋范围（§十一），不展开设计。

## 二、设计原则与范围

### 2.1 设计原则

1. **分类用户拍板，模型辅助**：四象限分类只能由用户明确回答，模型可以建议、不得代答；模型拿到用户明确回答后才能将分类与时间、内容一起提交给程序
2. **时间规则代码说了算**：滑动（72h）、提醒（24h）、默认完成（到达截止时刻）全部由程序结算，不依赖模型自觉；prompt 只负责让模型少犯错
3. **三要素硬校验**：时间、内容、分类任缺其一，程序拒绝写入并向模型报错
4. **防轰炸**：主动提醒只有两种情况（滑红一次、重要紧急剩 24h 一次）；不重要的（蓝/黄）全程静默
5. **用户拥有最高修改权**：未完成态任务的四个属性不是固定不变的量，随时随用户需求变更（UI 或口述均可）
6. **以列表为准**：UI 手动修改导致的数据变化是常态，模型侧以列表最新内容为准，不纠结记忆偏差
7. **纯插件**：不改宿主一行代码；prompt 修改经插件机制注入，不碰宿主源码

### 2.2 一期范围（最低实现形态）

功能一（四象限待办）+ 功能三（独立 UI 三形态）。

### 2.3 二期范围

功能二（大目标拆解小目标）+ 功能四（QQ 通道使用打磨）。本文档不展开，见 §十一。

### 2.4 非目标（一期明确不做）

- 不做每日例行/周期任务（功能二二期再议）
- 不做 QQ 主动提醒外发（当前插件 API 无消息发送通道；提醒只落本地聊天 + Toast）
- 不做多设备同步、数据导出
- 不做宿主设置页 iframe 面板（独立窗口是唯一 UI）
- 不修改宿主任何代码

## 五、功能一：四象限待办

### 5.1 登记入口（对话流）

用户告诉昔涟自己有什么事项要做，分流如下：

- 用户**直接要求**将此事项记入待办列表 → 进入属性收集
- 用户**没有明确要求** → 昔涟主动询问"是否要记入待办列表"
  - 回答**是** → 进入属性收集
  - 回答**否** → 不登记，对话自然继续

### 5.2 四属性

每个待办事项都有四条属性：

| 属性 | 一句话说明 |
|---|---|
| **时间** | 明确截止时间（最低到日期）或"无明确截止时间"，二者其一 |
| **内容** | 事项内容本身 |
| **四象限分类** | "重要紧急"、"重要不紧急"、"不重要紧急"、"不重要不紧急"四词之一 |
| **完成状态** | "未完成"、"已完成"、"默认完成"三态之一 |

录入时，**前三项（时间、内容、四象限分类）必须齐备**才能写入待办列表；**完成状态不强制提供**，录入即默认"未完成"。

#### 属性一：时间

- 二者其一：① **明确截止时间**——格式"xx年xx月xx日xx小时xx分钟"，**最低标准为 xx年xx月xx日**（有时分记时分，没有时分但有日期可正常记入）；② 字面值**"无明确截止时间"**——这本质上也是时间信息，是合法取值，正常记录
- **用途和作用**：时间是三项自动机制的判断依据——象限滑动（剩余 ≤72 小时）、主动提醒（重要紧急剩余 ≤24 小时）、默认完成转换（到达截止时间仍无人在场处理）；填"无明确截止时间"的事项，这三项机制均不触发

#### 属性二：内容

- 事项内容本身，无需赘述
- **用途和作用**：识别与展示事项的依据

#### 属性三：四象限分类

- 只能是四个词之一："重要紧急"（红）、"重要不紧急"（绿）、"不重要紧急"（黄）、"不重要不紧急"（蓝）
- **分类由用户判断，模型辅助**：模型可以给建议，但必须等到用户对分类做出明确回答后，才能将分类与时间、内容一起提交给程序
- **用途和作用**：分类决定事项在四象限中的归属和完成前的字体颜色（红/绿/黄/蓝）；同时决定滑动资格与提醒资格（§5.4、§5.5）

#### 属性四：完成状态

- 三态：**未完成**、**已完成**、**默认完成**
- **用途和作用**：完成状态决定字体颜色（完成前由分类决定；已完成标**亮灰色**，默认完成标**暗灰色**）、事项的去留（完成态退出待办列表、进入"已完成列表"）以及机制资格（完成态不再滑动、不再提醒）

| 状态 | 进入条件 |
|---|---|
| 未完成 | 录入默认 |
| 已完成 | 用户在 **UI 界面手动修改**，或**明确告诉模型**"这项任务已完成"，由模型标为已完成 |
| 默认完成 | **有截止时间**的任务到达截止时间时仍是"未完成"（用户既没在 UI 改、也没告诉模型已完成），自动转为 |

- 无截止时间的事项永远不会自动转"默认完成"，停在"未完成"直到用户主动完成

### 5.3 双保险机制

**措施一：代码硬校验（真兜底）**

- 程序要求模型必须提供**前三项属性（时间、内容、四象限分类）**才能写入待办列表，任缺其一则**拒绝执行写入**，并向模型返回报错信息："缺时间"、"缺内容"、"缺分类"
- 时间字段校验：取值必须是"具体时间（最低到日期）"或"无明确截止时间"二者其一——**"无明确截止时间"不算缺时间**；字段整体缺失、或值非法（两种形式都不是）同样拒写

**措施二：prompt 软规范**

- 通过**插件机制**修改 prompt（PromptProvider 注入，事实 #10），**不直接改宿主代码**
- 注入内容：① 前三项属性必齐的要求；② 时间格式要求（"xx年xx月xx日xx小时xx分钟或无明确截止时间二者其一"、日期为最低标准）；③ 四象限分类格式要求（只能是四词之一）；④ 追问规则（表述不清/无法确切判断时追问）

### 5.4 象限滑动

- 滑动是分类属性的**真实变更**：条件满足时，事项的四象限分类属性本身被改写
- **滑动的唯二判断条件**（二条件同时满足，则执行滑动）：
  1. 事项的分类属性是否为"重要不紧急"和"不重要不紧急"其中之一？
  2. 如果有截止时间，距截止时间是否只剩 72 小时？（三天按 72 小时计，按小时计算；时间信息只有年月日、无小时分钟的，以截止日期的 **00 时 00 分**为基准）
- **滑动方向**：前者滑为"重要紧急"，后者滑为"不重要紧急"；"重要紧急"与"不重要紧急"是终点，不再滑动
- 无截止时间的事项：条件 2 无法满足，永不滑动
- 滑动只作用于"未完成"任务
- **自动滑回**：截止时间被修改、剩余时间退出 72h 窗口时，**由滑动改写的**分类自动改回原分类，再次进入窗口时按正常规则再次滑动（实现语义：滑动发生时记录原分类作为滑回目标）
- 自动滑回只撤销滑动产生的变更，用户手动修改的分类不属于滑动、不受影响
- （自然推论，写明以防歧义：72h 窗口内手动把分类改回绿/蓝的，滑动条件仍满足时会再次滑红——想让事项退出紧急状态，应修改截止时间）

### 5.5 主动提醒

主动发消息通知只有两种情况：

1. **重要不紧急滑为重要紧急时**，提醒一次
2. **重要紧急事项截止时间只剩 24 小时时**，提醒一次

时间信息只有年月日、无小时分钟的，同样以截止日期的 **00 时 00 分**为基准。

| 事项分类 | 滑动 | 主动提醒（最多） |
|---|---|---|
| 重要不紧急（绿） | 剩余 ≤72h → 重要紧急 | 滑红一次 + 剩余 ≤24h 一次 = 两次 |
| 重要紧急（红，直接登记） | 不滑动 | 剩余 ≤24h 一次 |
| 不重要不紧急（蓝） | 剩余 ≤72h → 不重要紧急 | 零（蓝滑黄不提醒） |
| 不重要紧急（黄） | 不滑动 | 零 |
| 无明确截止时间 | 永不滑动 | 零 |

- 提醒只对"未完成"任务生效
- **一轮重置**：截止时间被修改 = 新的一轮，两类提醒标记清零，重新进入窗口可再次提醒
- 提醒落点：本地聊天 + Toast（经 scheduler 通道，§九）；**QQ 手机端收不到主动提醒**（插件 API 无消息发送通道，见 §2.4）
- **离线漏提醒与开机补检**：插件运行依赖主进程在线（事实 #11）——到了提醒时间而主进程不在线，提醒无法送达，这是无法更改的架构事实。补漏机制见 §9.3：每次 Cyrene 开机时检查是否有需要主动提醒的任务，无则静默，有则按正常提醒流程提醒

### 5.6 属性修改、删除与反悔

**用户拥有最高修改权**：未完成态任务的四个属性（时间、四象限分类、内容、完成状态）不是固定不变的量，随时随用户需求变更（如果有的话）——可通过 **UI 界面**或**口述让 AI** 修改。

- **纯删除**：允许。待办列表里的任务可在 UI 直接删除；**口述删除也可**（工具面含删除工具），但 prompt 明确约束：**必须是用户明确要求删除的才能删除**
- **反悔**（针对完成态任务，如发现默认完成的任务其实没做完）：不存在"原地改回未完成"——逻辑为**删除原任务 + 重走新建流程**：模型根据已有信息预填内容，新截止时间由用户定，分类沿用也须用户明确确认；UI 界面手动反悔是同一逻辑（删除、创造新的待办事项）
- 完成态任务不提供属性修改，可做的只有：查看（已完成列表）、纯删除、反悔

## 六、功能三：独立 UI（三种形态）

### 6.1 窗口形态与入口

- 独立桌面窗口，**不是**宿主设置页里的 iframe 面板
- 入口：宿主"功能插件"卡片/聊天侧插件面板的"打开"按钮（宿主 open() 生命周期钩子，事实 #9）
- 自绘标题栏（无边框窗口），带最小化/关闭；关闭窗口不卸载插件（与先例一致）
- 窗口配置沿用先例：本地单文件页面、无远程加载、无用户可控 HTML 注入，故接受该配置（安全权衡说明）

### 6.2 三种形态与切换

| 形态 | 名称 | 内容 |
|---|---|---|
| 1 | 四象限视图 | 左待办列表 + 右四象限 |
| 2 | 日历视图 | 左待办列表 + 右日历 |
| 3 | 已完成列表 | 已完成任务集中查看 |

三种形态通过**切换按钮**切换（切换控件置于窗口顶部）。

### 6.3 形态一：四象限视图

- **最左边**：从上往下列出所有记录在待办列表的待办事项（即全部"未完成"任务）
- **右边**：四象限区域，不同象限不同对应颜色，待办事项按各自的四象限分类放入对应象限
- 字体颜色规则按功能一：未完成 = 分类色（红/绿/黄/蓝）
- 象限滑动后的任务按"当前分类"归格——滑动是真实变更（§5.4），展示天然一致

### 6.4 形态二：日历视图

- **最左边**：待办列表，同形态一
- **右边**：日历，可以看到哪天有哪些待办事项
  - 从属大目标的确定时间小目标**不显示**在日历格里（该条自功能二上线起生效，一期无小目标，规则空置）
- **点开某一天** → 进入这一天的 **24 小时视图**：可以看到这天的待办事项及每个事项的小时时间（如果有的话）；同样，小目标在这里可见（二期生效）
- 只有日期没有时分的事项，在 24 小时视图中显示为"全天"条目；无截止时间的事项不出现在日历/24 小时视图中

### 6.5 形态三：已完成列表

- 专门用于**保存并让用户查看**已完成的任务（已完成 + 默认完成两类）
- 字体颜色按功能一规则：已完成 = **亮灰**，默认完成 = **暗灰**
- 条目保留原分类信息展示，颜色仍按完成态的灰阶走

### 6.6 UI 操作与功能一规则的对应

功能一的"用户最高修改权"在 UI 中的落点（具体交互形式为默认设计，可调）：

| 操作 | 作用对象 | 对应功能一规则 |
|---|---|---|
| 勾选/标记完成 | 未完成任务 | 完成状态 → 已完成 |
| 编辑属性（时间/分类/内容） | 未完成任务 | 最高修改权（UI 路径） |
| 删除 | 待办列表任务 | 纯删除 |
| 删除 + 新建 | 完成态任务 | 反悔（重走新建流程，新截止时间用户定） |

- UI 手动修改导致的数据变化，以列表最新内容为准（模型侧由 prompt 漂移对齐规则配合，§九）

## 七、数据模型

存储于插件 PluginStorage，key `tasks`（单 JSON 数组）。**存储层全同步读写（事实 #3），store 的读-改-写全程不夹 await，天然免并发写竞争**。

```ts
type Quadrant = "red" | "green" | "yellow" | "blue";
// red=重要紧急 green=重要不紧急 yellow=不重要紧急 blue=不重要不紧急
type Status = "pending" | "done" | "auto-done";
// pending=未完成 done=已完成(用户) auto-done=默认完成(到点自动)

interface Task {
  id: string;              // crypto.randomUUID()
  content: string;         // 属性二：内容
  deadline: string | null; // 属性一："YYYY-MM-DD HH:mm" | "YYYY-MM-DD"（只有日期按 00:00 计）| null(无明确截止时间)
                           // 字段必须存在——null 是合法值，缺字段/非法格式才是"缺时间"
  quadrant: Quadrant;      // 属性三：用户拍板；滑动会真实改写此字段
  status: Status;          // 属性四：录入默认 "pending"
  slidFrom?: Quadrant;     // 滑动结算时记录的原分类，用于自动滑回；用户手动改分类时清除
  reminded?: {             // 提醒标记：值为"已提醒时对应的 deadline 字符串"
    slide?: string;        // 滑红提醒——deadline 变更（字符串不等）即视为新的一轮
    due24?: string;        // 24h 提醒——同上
  };
  createdAt: number;
  completedAt?: number;    // 转入完成态的时刻（已完成列表排序用）；完成态长期保存，不做清理
}
```

要点：

- **分类存储英文枚举、展示中文四词**，映射：red=重要紧急、green=重要不紧急、yellow=不重要紧急、blue=不重要不紧急；工具参数接受中文四词，校验后落枚举
- **deadline 恒存在**（string 或 null）：null 即"无明确截止时间"——保证"缺时间"报错只发生在字段缺失或值非法时
- **只有日期的 deadline 按 `YYYY-MM-DD 00:00` 参与 72h/24h 计算**
- 滑动改写 `quadrant` 前把原值记入 `slidFrom`；自动滑回 = `quadrant ← slidFrom` 并清除该字段；用户手动改分类时直接覆盖并清除 `slidFrom`
- 完成态任务**长期保存**（无 30 天清理——已完成列表的语义就是保存与查看）

## 八、Agent 工具面

工具 id 一律带插件前缀 `quadrant-todo_`（宿主校验，事实 #1 语境）。五个工具，全部只操作插件自有数据。

### 8.1 `quadrant-todo_add_task` —— 登记待办

```
参数：content(string, 必填), deadline(string|"null", 必填), quadrant(中文四词, 必填)
校验：content 缺失 → 报错"缺内容"；deadline 缺失或值非法 → 报错"缺时间"；
     quadrant 缺失或非四词 → 报错"缺分类"；任一报错则拒绝写入
行为：写入任务（status=pending，slidFrom/reminded 为空），返回登记结果
```

- **工具描述中强制约定**：agent 须先完成属性收集（分类获用户明确回答、时间与内容以用户表述为准、缺啥追问）后才调用；调用前不做整体复述确认

### 8.2 `quadrant-todo_update_task` —— 修改属性

```
参数：id(必填), content?/deadline?/quadrant?/status?（至少一项）
行为：更新对应属性；deadline 变更时触发结算（自动滑回 + 提醒标记重置，§九）；
     quadrant 手动变更时清除 slidFrom
```

对应"口述让 AI 修改属性"路径。

### 8.3 `quadrant-todo_complete_task` —— 标记完成

```
参数：id(必填)
行为：status → "done"，记 completedAt；用户明确告知"已完成"时由模型调用
```

### 8.4 `quadrant-todo_delete_task` —— 删除

```
参数：id(必填)
行为：从列表移除记录（不新建）
描述约束：必须是用户明确要求删除的才能调用，禁止自行判断清理
```

### 8.5 `quadrant-todo_list_tasks` —— 查询

```
参数：scope("active" | "completed" | "all", 默认 "active")
行为：返回对应列表的实际内容；模型回答"我有什么要做"以此为准，不以记忆为准
```

### 8.6 反悔的实现

反悔不设独立工具 = `delete_task`（旧任务）+ `add_task`（新任务，模型按旧信息预填 content/quadrant 建议，deadline 由用户给新值）。对话流：用户说"那条没做完" → 模型确认 → 删旧 → 按新建流程收集新时间 → 写入。

## 九、prompt 注入与结算机制

### 9.1 PromptProvider 注入清单（prompts.ts）

通过 registerPromptProvider 常驻注入，内容八条：

1. 前三项属性（时间、内容、分类）必齐，缺则程序拒写并报"缺时间/缺内容/缺分类"
2. 时间格式："xx年xx月xx日xx小时xx分钟"或"无明确截止时间"二者其一；日期为最低标准
3. 分类只能是四词之一："重要紧急/重要不紧急/不重要紧急/不重要不紧急"
4. 追问规则：用户没表述清楚、或无法从上下文确切判断时，必须追问
5. 登记入口分流：用户未明确要求记入时，主动询问"是否要记入待办列表"，同意才收集
6. 删除约束：必须是用户明确要求删除的才能删除
7. **数据漂移对齐**：若待办列表/已完成列表的个数与内容同上下文记忆对不上，说明用户手动修改过（UI），无需纠结，以列表最新内容为准（查询用 `list_tasks`）
8. 反悔流程：完成态任务"没做完" → 删除旧任务 + 重走新建流程，新截止时间由用户定，分类沿用也须用户明确确认

### 9.2 结算器（settle.ts）

结算 = 对"到点该发生的事"做真实变更。三类结算：滑动（含滑回）、默认完成转换、提醒触发。

**结算时机（三路）**：

- **开机补检**：宿主每次启动（插件 register）时首轮扫描——先补结算（滑动/滑回/默认完成按当前时刻判定），再检查漏掉的提醒（§9.3）
- **写时结算**：任何写操作（工具调用、UI IPC）落地前后，对该任务即时结算——尤其 deadline 变更（滑回 + 提醒重置即时生效）
- **定时扫描**：插件内定时器周期扫描全部未完成、有 deadline 的任务（间隔默认 5 分钟，实现层可调）

**提醒发送通道**：结算判定"该提醒"后，经 scheduler 注册 mode:"chat" 任务发送——落本地聊天 + Toast（事实 #6，xiaomi-health 同款）；**任务须用户在宿主 UI 授权**（默认 enabled:false），一期验收含此步骤。QQ 手机端收不到主动提醒（§2.4）。

### 9.3 开机补检（离线漏提醒的补漏机制）

**事实**：插件运行依赖主进程在线（事实 #11）——到了主动提醒的时间而主进程不在线，提醒无法送达，这是架构事实、无法更改。

**补漏机制**：每次 Cyrene 开机时，结算器首轮扫描检查是否有需要主动提醒的任务——

- **无** → 静默，不做任何打扰
- **有** → 按正常提醒流程提醒

"需要提醒的"判定（针对仍未完成的任务，完成态不提醒）：

- 已滑红（本次结算中滑红、或离线期间跨过 72h 点经补结算滑红）且滑红提醒未标记 → 按正常流程补滑红提醒
- 已进入 24h 窗口（剩余 ≤24h）且 24h 提醒未标记 → 按正常流程补 24h 提醒

补发的提醒与在线时正常触发的提醒完全同形（一次、本地聊天 + Toast、标记照记），不存在"补发模式"的特殊文案。开机后各提醒仍受一轮一次约束，不会重复轰炸。

## 十、一期验收（DoD）

1. 构建产物拷入 `%APPDATA%\Cyrene\plugins\quadrant-todo\`，宿主重启后插件加载无报错（apiVersion=1）
2. 本地对话登记全流程：直接要求 / 昔涟主动询问两种入口都能走通；分类必须用户明确回答
3. 三要素硬校验：缺任一项返回对应报错（"缺时间"/"缺内容"/"缺分类"），"无明确截止时间"可正常录入
4. 滑动结算：绿/蓝任务剩 ≤72h（按小时、日期按 00:00）真实改写分类；红/黄不再滑动；改 deadline 滑回且 `slidFrom` 清理正确
5. 提醒：滑红提醒一次；红任务剩 ≤24h 提醒一次；改 deadline 后重新进入窗口可再次提醒（一轮重置）；经 scheduler 授权后本地聊天 + Toast 可见
6. 默认完成：有 deadline 任务过截止时刻仍"未完成" → 自动转"默认完成"；无 deadline 任务不转
7. UI 三形态可用：四象限视图（左列表右矩阵、分类入格）、日历视图（点日期进 24h 视图、全天条目）、已完成列表（亮灰/暗灰）
8. UI 操作写回：勾完成、改属性、删除、反悔（删+新建）全部落库正确
9. 查询：`list_tasks` 按实际数据回答；模型在 UI 手改后不再依赖旧记忆
10. prompt 注入八条全部生效（含删除约束、漂移对齐）
11. 开机补检：宿主重启后，离线期间跨过提醒时刻的任务按正常流程补提醒一次，无漏提醒时静默
