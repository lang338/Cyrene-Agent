## 一、这个插件是什么（命名与定义）

- **定义**：该插件是一个协助用户规划时间，制定计划的辅助型插件
- **插件全名**：四象限待办——昔涟帮你记录待办事项
- **简称**：四象限待办
- **工程 id**：`quadrant-todo`（工具前缀 `quadrant-todo_*`）

用户把"后面要做的事"告诉昔涟，她按**重要 × 紧急**四象限整理成彩色清单：重要紧急（红）、重要不紧急（绿）、不重要紧急（黄）、不重要不紧急（蓝），随时间自动滑动优先级、自动提醒、自动结算完成状态；桌面独立窗口提供待办全景（四象限 / 日历 / 已完成列表三种形态）。

## 二、设计原则
1. 插件基于宿主设计，通过已有的插件接口实现功能，而非修改宿主代码
2. 用户拥有最高修改权：程序内保留的所有有关用户信息（如待办事项、时间、四象限分类、完成状态）都以用户的最新修改或口述为准
3. 模型仅能依靠已有的信息向用户提出参考性建议，不能擅自对用户的待办事项或后续计划进行揣测并修改的情况（除非用户明确要求），用户通过UI 手动修改导致的数据变化是常态，模型侧以列表最新内容为准，不纠结记忆偏差
4. 明确主动提醒规则：滑动（72h）、提醒（24h）、默认完成（到达截止时刻）全部由程序结算，不依赖模型自觉；prompt 只负责让模型少犯错

### 3.1 功能一：四象限待办登记，修改及提醒：
#### 3.11 登记入口（对话流）

三个入口：
1. 昔涟从上下文留意到用户可能的需求（如记录待办事项，规划后续任务），并主动询问是否需要记录或规划，如果为是，进入下一步；如果为否，对话自然继续。
若需求为记录待办事项，进入属性收集。
若需求为规划后续任务，进入功能二。

2. 用户主动要求记录待办事项或规划后续任务。
若需求为记录待办事项，进入属性收集。
若需求为规划后续任务，进入功能二。

3. 用户手动在ui界面进行修改

#### 3.12 四属性

每个待办事项都有四条属性：

| 属性 | 一句话说明 |
|---|---|
| **时间** | 明确截止时间（最低到日期）或"无明确截止时间"，二者其一 |
| **内容** | 事项内容本身 |
| **四象限分类** | "重要紧急"、"重要不紧急"、"不重要紧急"、"不重要不紧急"四词之一 |
| **完成状态** | "未完成"、"已完成"、"默认完成"三态之一 |

录入时，**前三项（时间、内容、四象限分类）必须齐备**才能写入待办列表；**完成状态不强制提供**，录入即默认"未完成"。

##### 属性一：时间
- 二者其一：① **明确截止时间**——格式"xx年xx月xx日xx小时xx分钟"，**最低标准为 xx年xx月xx日**（有时分记时分，没有时分但有日期可正常记入）；② 字面值**"无明确截止时间"**——这本质上也是时间信息，是合法取值，正常记录
- **用途和作用**：时间是三项自动机制的判断依据——象限滑动（剩余 ≤72 小时）、主动提醒（重要紧急剩余 ≤24 小时）、默认完成转换（到达截止时间仍无人在场处理）；填"无明确截止时间"的事项，这三项机制均不触发
##### 属性二：内容
- 事项内容本身，无需赘述
- **用途和作用**：识别与展示事项的依据
##### 属性三：四象限分类
- 只能是四个词之一："重要紧急"（红）、"重要不紧急"（绿）、"不重要紧急"（黄）、"不重要不紧急"（蓝）
- **分类由用户判断，模型辅助**：模型可以给建议，但必须等到用户对分类做出明确回答后，才能将分类与时间、内容一起提交给程序
- **用途和作用**：分类决定事项在四象限中的归属和完成前的字体颜色（红/绿/黄/蓝）；同时决定滑动资格与提醒资格（3.14、3.15）
##### 属性四：完成状态
- 三态：**未完成**、**已完成**、**默认完成**
- **用途和作用**：完成状态决定字体颜色（完成前由分类决定；已完成标**亮灰色**，默认完成标**暗灰色**）、事项的去留（完成态退出待办列表、进入"已完成列表"）以及机制资格（完成态不再滑动、不再提醒）

| 状态 | 进入条件 |
|---|---|
| 未完成 | 录入默认 |
| 已完成 | 用户在 **UI 界面手动修改**，或**明确告诉模型**"这项任务已完成"，由模型标为已完成 |
| 默认完成 | **有截止时间**的任务到达截止时间时仍是"未完成"（用户既没在 UI 改、也没告诉模型已完成），自动转为 |

- 无截止时间的事项永远不会自动转"默认完成"，停在"未完成"直到用户主动完成

#### 3.13 双保险机制

**措施一：代码硬校验**

- 程序要求模型必须提供**前三项属性（时间、内容、四象限分类）**才能写入待办列表，任缺其一则**拒绝执行写入**，并向模型返回报错信息："缺时间"、"缺内容"、"缺分类"
- 时间字段校验：取值必须是"具体时间（最低到日期）"或"无明确截止时间"二者其一——**"无明确截止时间"不算缺时间**；字段整体缺失、或值非法（两种形式都不是）同样拒写

**措施二：prompt 软规范**

- 通过**插件机制**修改 prompt（PromptProvider 注入），**不直接改宿主代码**
- 注入内容：① 前三项属性必齐的要求；② 时间格式要求（"xx年xx月xx日xx小时xx分钟或无明确截止时间二者其一"、日期为最低标准）；③ 四象限分类格式要求（只能是四词之一）；④ 追问规则（表述不清/无法确切判断时追问）

#### 3.14 象限滑动

- 滑动是分类属性的**真实变更**：条件满足时，事项的四象限分类属性本身被改写
- **滑动的唯二判断条件**（二条件同时满足，则执行滑动）：
  1. 事项的分类属性是否为"重要不紧急"和"不重要不紧急"其中之一？
  2. 如果有截止时间，距截止时间是否只剩 72 小时？（三天按 72 小时计，按小时计算；时间信息只有年月日、无小时分钟的，以截止日期的 **00 时 00 分**为基准）
- **滑动方向**：前者滑为"重要紧急"，后者滑为"不重要紧急"；"重要紧急"与"不重要紧急"是终点，不再滑动
- 无截止时间的事项：条件 2 无法满足，永不滑动
- 滑动只作用于"未完成"任务
- **自动滑回**：截止时间被修改、剩余时间退出 72h 窗口时，**由滑动改写的**分类自动改回原分类，再次进入窗口时按正常规则再次滑动（实现语义：滑动发生时记录原分类作为滑回目标）
- 自动滑回只撤销滑动产生的变更，用户手动修改的分类不属于滑动、不受影响
- （自然推论，写明以防歧义：72h 窗口内手动把分类改回绿/蓝的，滑动条件仍满足时会再次滑红——想让事项退出紧急状态，应修改截止时间）

#### 3.15 主动提醒

主动发消息通知只有两种情况：

1. **重要不紧急滑为重要紧急时**，提醒一次
2. **重要紧急事项截止时间只剩 24 小时时**，提醒一次

时间信息只有年月日、无小时分钟的，同样以截止日期的 **00 时 00 分**为基准。

| 事项分类 | 滑动 | 主动提醒（最多） |
|---|---|---|
| 重要不紧急（绿） | 剩余 ≤72h → 重要紧急 | 滑红一次 + 剩余 ≤24h 一次 = 两次 |
| 重要紧急（红，直接登记） | 不滑动 | 剩余 ≤24h 一次 |
| 不重要不紧急（蓝） | 剩余 ≤72h → 不重要紧急 | 零（蓝滑黄不提醒） |
| 不重要紧急（黄） | 不滑动 | 零 |
| 无明确截止时间 | 永不滑动 | 零 |

- 提醒只对"未完成"任务生效
- **一轮重置**：截止时间被修改 = 新的一轮，两类提醒标记清零，重新进入窗口可再次提醒
- 提醒落点：**本机系统通知**（核心通道，插件经 Electron 原生通知直发，无需任何授权）+ **QQ 私聊外发**（移动端扩展通道，仅 QQ NapCat 单渠道，须用户配置，见 3.42）。**不使用宿主定时任务通道**——其授权流程与"跨重启作废"问题与提醒必须可靠送达冲突，弃用缘由见 §八
- **离线漏提醒与开机补检**：插件运行依赖主进程在线——到了提醒时间而主进程不在线，提醒无法送达，这是无法更改的架构事实。补漏机制：每次 Cyrene 开机先扫一轮结算，**仍在提醒窗口内**的错过提醒按正常流程补发（本机通知与 NapCat 外发一并补）；已过截止时刻的任务按规则转默认完成、不再补发，无漏则静默
- **定位边界（2026-11-04 增）**：提醒是"提前预警"（滑红/剩 24h 两次），**不是闹钟**——截止时刻本身不提醒，到点无人处理即静默转默认完成。"到点叫我一声"的一次性闹钟需求属**宿主定时任务**的能力范围，模型遇到这类需求应引导用户改用定时任务，不为它登记待办

#### 3.16 属性修改、删除与反悔

**用户拥有最高修改权**：未完成态任务的四个属性（时间、四象限分类、内容、完成状态）不是固定不变的量，随时随用户需求变更（如果有的话）——可通过 **UI 界面**或**口述让 AI** 修改。

- **纯删除**：允许。待办列表里的任务可在 UI 直接删除；**口述删除也可**（工具面含删除工具），但 prompt 明确约束：**必须是用户明确要求删除的才能删除**
- **反悔**（针对完成态任务，如发现默认完成的任务其实没做完）：不存在"原地改回未完成"——逻辑为**删除原任务 + 重走新建流程**：模型根据已有信息预填内容，新截止时间由用户定，分类沿用也须用户明确确认；UI 界面手动反悔是同一逻辑（删除、创造新的待办事项）
- 完成态任务不提供属性修改，可做的只有：查看（已完成列表）、纯删除、反悔

## 3.2 功能二：长时限大目标任务辅助拆分为短时间小目标任务

用户的需求不全是"明天 7 点交作业"这类明确事项，还可能是"我想学英语过四六级""我想每天跑步锻炼身体""我想学画画""我想学某门课程"这类**长时限大目标**——持续数周甚至数月，且用户往往没想好怎么实现。本功能即针对这类需求的辅助拆解能力：大目标与其拆解出的小目标构成**树形结构**，小目标从属大目标。

#### 3.21 入口与触发（对话流）

两类情形分流：

1. 用户表达的大目标**已有具体规划**（已经想好拆成哪些事、各有时间）→ 直接按普通登记流程录入：先登记大目标，再逐条录入其下小目标，无需提议
2. 用户表达的大目标**只有目标没有规划**（表述里没有具体时间或步骤）→ 昔涟主动提议："要不要把它拆解成有明确时限的小目标？"
   - 用户同意 → 进入拆解引导
   - 用户拒绝 → 放弃，**同一目标不再主动提起**，除非用户主动再提

**模型的角色定位**：引导与建议——告诉用户"可以怎么拆"（阶段划分、先做哪几步）、给予鼓励和情绪价值；**小目标的内容由用户自行决定**，模型可以提供参考方案，用户确认无误（或修改后确认无误）后才能写入。不被允许的是模型推断可能的拆解（实现）方式后绕过用户确认这一环自行写入。

（写明以防歧义：提议与拆解都只发生在对话里，最终写入仍走功能一的工具面与硬校验。）

#### 3.22 大目标的属性

| 属性        | 规则                                                                          |
| --------- | --------------------------------------------------------------------------- |
| **时间**    | "xx年xx月xx日"或"无明确截止时间"二者其一，格式同功能一；"三个月内过四级"这类模糊表述，由模型帮助用户收敛成一个明确日期或"无明确截止时间" |
| **内容**    | 同普通任务                                                                       |
| **四象限分类** | 由用户定（模型辅助），同普通任务；**其下全部小目标的分类从属此分类，不独立判断**                                  |
| **完成状态**  | 同功能一三态（未完成/已完成/默认完成均可出现，见 3.25）                                              |

#### 3.23 小目标的属性

- **内容**：同普通任务
- **时间**：精确时限，**最低到时分**——小目标存在的意义就是精确执行
- **四象限分类**：**从属大目标，不独立分类**——录入时无需用户逐个拍板，展示颜色随大目标分类走
- **自定义提醒**：**默认不提醒**。拆解/录入时昔涟逐个询问"这个小目标需要提醒吗？"；需要的话由用户确定提醒方式，粒度不限：每天某时刻、每两天某时刻、更长间隔、单次时刻均可；也允许**先只定前几个小目标的提醒，后面的以后再定**
- **模型权限边界**：小目标提醒由模型**按用户要求**设置或修改；用户未要求的，模型不得主动改动

#### 3.24 机制资格（与功能一自动机制的关系）

| 机制   | 大目标         | 小目标                       |
| ---- | ----------- | ------------------------- |
| 象限滑动 | 不参与         | 不参与（分类从属，永不滑动）            |
| 主动提醒 | 无           | 仅自定义提醒，**不遵循 72h/24h 规律** |
| 默认完成 | 不适用（见 3.25） | 到点自动转                     |

- 小目标自定义提醒的送达通道与功能一相同：本机系统通知（核心通道）+ 移动端 QQ NapCat 通道（功能四，已配置时）
- 周期提醒（每天/每 N 天某时刻）随本功能实现，数据模型留扩展位

#### 3.25 完成机制

- **小目标**：到点仍"未完成" → 自动转"**默认完成**"（同功能一）；手动标完成同功能一
- **大目标 · 默认完成**（有时限）：**已到时限 且 所有小目标已完成**——两个条件中较晚满足的时刻，由程序自动转"默认完成"（标暗灰，同功能一"程序自动转入"的口径）。提前全部完成的大目标就挂着等到时限；想让它亮灰，时限前手动标一下即可
- **大目标 · 手动标完成**：用户手动标（UI 勾选或口述）时，其下**全部未完成小目标连带标为"已完成"**（亮灰，非默认完成）
- **大目标 · 无时限**：永不自动完成；小目标全部完成后仍等待用户手动标
- （反向不存在：小目标各自的完成不要求大目标完成，小目标先于大目标完成是常态）

#### 3.26 修改、删除与反悔

- **用户最高修改权同功能一**：未完成态大目标/小目标的属性随时可改（UI 或口述）
- **改大目标分类** → 其下小目标分类跟随变动（从属关系的自然结果）
- **改小目标截止时间** → 默认完成判定按新时间走；其自定义提醒**不自动调整**，需要调整时由用户提出（模型权限边界）
- **删除大目标** = 连带删除其下全部小目标（树形整体删除）；口述删除时模型须先向用户确认连带范围，UI 删除给出连带提示
- **删除小目标** = 纯删除该条，不影响大目标与其余小目标
- **小目标反悔**：按功能一"删除 + 重走新建"逻辑，重录时仍挂原大目标，不落为顶层普通任务
- 完成态大目标可做：查看（待办树/已完成列表）、纯删除；**反悔暂不提供**——如需继续推进，直接新建大目标重新拆解（默认设计，可调）

#### 3.27 UI 展示（与功能三的对应）

- **待办树**：形态一/形态二左侧的待办列表升级为树形——大目标为父节点，其下小目标为子节点；普通任务仍为顶层条目
- **四象限视图**：小目标按从属分类入对应象限格；大目标不入格（仅呈现于待办树）
- **日历 / 24 小时视图**：小目标按精确时限显示，大目标不显示
- **过期态**：到期但未完成的大目标在树上以过期样式呈现（只展示，不提醒——功能二无主动提醒规则不变）
- **已完成列表**：小目标按功能一灰阶规则（已完成亮灰/默认完成暗灰）；大目标完成后同列表可见（亮灰）

（实现注记：树形关系、周期提醒字段、机制资格标志与联动结算属实现侧细节，随实现展开，文档不约束；小目标分类继承父级，双保险校验按归属校验、不算缺分类。）

#### 3.28 prompt 软规范

注入分两部分：先按流程向模型讲清这个功能如何运转（理解流程后判断自然对齐），再给预判风险节点的处置。仅写功能二特有的内容，与常驻规范（属性校验、以列表为准、对话体验等）重复的不重复注入。

**第一部分：功能运行流程**

1. **识别与提议**：用户说出一个只有目标、没有具体时间或步骤的长期打算时，提议拆解成有明确时限的小目标；用户已经想好拆成什么的，跳过提议直接引导录入；提议被拒绝就不再提
2. **引导拆解**：用户同意后，模型给拆解思路上的建议、鼓励用户自己定小目标；每确定一条就录入一条——内容用用户说的，时间精确到时分，分类不用问（自动随大目标），逐个问一句"这个小目标要提醒吗"，要的话时刻和间隔全听用户的，只先定前几个也可以
3. **日常运转**：录入后小目标挂在大目标下随它走——分类随父级显示，不到点不响不动，到点没人管就自动转"默认完成"。大目标自己不响也不动，等"到了时限且小目标全部完成"才转"默认完成"（提前全完就挂着等时限）；到期时还没全完就继续等，最后一个小目标完成的时刻它跟着转
4. **用户干预**：用户随时可改可删——改大目标分类，小目标跟着换；改小目标时间只影响它自己的完成判定；手动标大目标完成时，剩余小目标连带完成；删大目标时小目标一并删

**第二部分：预判风险节点与处置**

| 风险节点 | 错误表现 | 处置方式 |
|---|---|---|
| 检测误判 | 没识别出大目标，或把已有规划的需求拿来推销 | 锚点：表述里没有具体时间或步骤才提议 |
| 反复推销 | 被拒绝后换个说法再提 | 同一目标不再主动提，除非用户重新提起 |
| 越权规划 | 模型自己编一套小目标直接写入 | 小目标内容必须由用户决定，模型只建议和引导 |
| 模糊时间乱填 | "三个月内"被随手填成一个日期 | 帮用户收敛成明确日期或"无明确截止时间"，结果经用户确认 |
| 提醒越权/遗漏 | 擅自加删改提醒；或录入时忘了问 | 只在用户要求时设置或修改；录入时逐个问过再录 |
| 连带操作误伤 | 删除/标完成时悄悄影响小目标 | 操作前向用户确认连带范围（删几个、完成几个） |

## 3.4 功能四：移动端主动提醒（QQ NapCat 通道）

本功能包含两个能力：**QQ 私聊口述使用**（被动，机制现成）与**主动提醒外发**（本节主体，唯一移动端渠道）。手机无 UI 页面——移动端的一切操作都是对话，一切提醒都是消息。

#### 3.41 QQ 私聊口述使用（被动通道）

- **机制**：插件工具注册进宿主共享工具池，QQ 私聊默认暴露全部工具（宿主"手机端工具权限"默认 all）；群聊禁用工具（宿主硬编码，防打扰设计）
- **能力范围**：登记、查询、修改、删除、反悔全部可用，与本地对话同规范、同数据、同硬校验——手机上记一笔和电脑上说一句完全等价
- **边界**：只能"录"不能"收"——主动提醒走 3.42；且依赖电脑端 Cyrene 在线（工具与提醒都挂主进程）
- 注意：宿主"手机端工具权限"开关若被改窄，插件工具将不在 QQ 端暴露

#### 3.42 主动提醒外发（QQ NapCat，唯一移动端渠道）

- **渠道选型**：只做 NapCat——OneBot 协议有标准化 HTTP 接口，插件可直连发送。其余渠道不做：QQ 官方机器人受平台主动消息限制（频控/场景），微信无标准化接口，飞书同理可扩展但暂不排
- **前提配置**（用户手动完成）：①NapCat 开启 HTTP API 服务（端口 + access token）；②在插件中配置 NapCat 地址、token、目标 QQ 号。**未配置时本通道整体跳过**，提醒只走本机系统通知，功能不受损（优雅降级）
- **文案生成**：登记/修改回合由昔涟根据任务内容**当场生成提醒文案**（功能一：滑红一条 + 剩 24h 一条；功能二小目标：随提醒设置生成），随任务属性存入列表——文案是模型针对该任务生成的自然表述，非固定模板。截止时间或分类修改进入新一轮时，文案随之重新生成
- **发送判定**：提醒时刻由插件结算触发（与 3.15/3.24 同源）；发送前校验该任务仍"未完成"且分类符合提醒条件——已完成、已删除、分类不符的不发
- **发送方式**：插件经 OneBot HTTP `send_private_msg`，以机器人 QQ 号向目标私聊发出；此链路与宿主自身的 NapCat 反向 WS 连接相互独立，互不影响
- **离线补发**：Cyrene 关机错过提醒时刻的，开机补检按正常流程补结算，本机通知与 NapCat 外发两条通道一并补发
- **失败处理**：NapCat 离线或发送失败仅记日志，不重试

#### 3.43 边界与说明

- **不进会话记录**：外发消息不经过宿主会话管线——用户回复这条提醒时，昔涟看得到回复（走正常接收管线），但她上下文里没有当初那条提醒，接不上"刚才提醒你的是……"。这是宿主渠道管线的架构边界，插件侧无法解决
- **口吻边界**：外发的是登记时生成的"昔涟口吻"预写文本，不是触发时刻实时生成——实时生成依赖宿主开放模型调用能力给插件，当前架构做不到（可向上游提需求）
- **配置面**：NapCat 地址/token/目标 QQ 号存于插件自有存储；配置入口随工作台（功能三）提供，默认设计可调

| 14 | 插件及一切能力运行依赖宿主主进程在线；主进程离线期间到点的提醒无法送达                                                                                       | 架构事实，无法更改——开机补检兜底（§8.2）                                          |
| 15 | 开发期即插即用：构建产物拷入宿主用户数据目录的插件文件夹，重启宿主即生效                                                                                      | 宿主启动时扫描加载                                                        |

## 五、数据模型

存储于插件自有键值存储，key `tasks`（单 JSON 数组）。存储层全同步读写，读-改-写不夹 await。

```ts
type Quadrant = "red" | "green" | "yellow" | "blue";
// red=重要紧急 green=重要不紧急 yellow=不重要紧急 blue=不重要不紧急
type Status = "pending" | "done" | "auto-done";
// pending=未完成 done=已完成(用户标记) auto-done=默认完成(程序自动转入)

interface Task {
  id: string;                // 唯一标识
  content: string;           // 属性二：内容
  deadline: string | null;   // 属性一："YYYY-MM-DD HH:mm" | "YYYY-MM-DD"（只有日期按当日 00:00 计）| null（无明确截止时间）
  quadrant: Quadrant;        // 属性三：用户拍板；滑动会真实改写此字段
  status: Status;            // 属性四：录入默认 "pending"
  createdAt: number;
  completedAt?: number;      // 转入完成态的时刻
  slidFrom?: Quadrant;       // 滑动结算时记录的原分类，用于自动滑回；用户手动改分类时清除
  reminded?: {               // 提醒标记：值为该轮提醒触发时对应的 deadline 字符串（判等防重复）
    slide?: string;          // 滑红提醒
    due24?: string;          // 24h 提醒
  };
  reminderTexts?: {          // 功能四外发文案：登记回合由模型生成、随任务存储（预写，非触发时生成）
    slide?: string;
    due24?: string;
  };
}
```

功能二字段预留（实现随功能二启动，字段先定型）：

```ts
// 挂在大目标名下的小目标附加字段
parentId?: string;                       // 所属大目标 id；顶层普通任务无此字段
reminder?: ReminderSpec | null;          // 小目标自定义提醒，默认 null（不提醒）
// ReminderSpec 二型：① 单次时刻（具体日期时间）② 周期（每 N 天 + 当日 HH:mm）
```

- **机制资格由数据形态推导**：带 `parentId` 的小目标与其大目标均不参与滑动；大目标无主动提醒；小目标仅有 `reminder` 指定的自定义提醒
- 大目标自动完成结算依赖树形关系：全部子目标完成 且 已到时限（两条件取较晚满足时刻）
- 配置存储：key `settings`（NapCat 地址 / access token / 目标 QQ 号）

## 六、工具面

五个工具，id 均带 `quadrant-todo_` 前缀，均声明 chat 内建（宿主会话白名单机制：仅内建工具进入昔涟日常对话的工具清单，其余需用户手动启用——不带此声明的工具在对话里整个不可见）：

| 工具              | 作用        | 关键约束                                             |
| :-------------- | :-------- | :----------------------------------------------- |
| `add_task`      | 登记待办      | 三要素齐备才可调用；调用前属性收集即确认，不做整体复述；分类表态自检必答                        |
| `update_task`   | 修改未完成待办属性 | 至少一项；改截止时间自动滑回并重置提醒（新一轮）；手动改分类清除滑动记录             |
| `complete_task` | 标记完成      | 仅用户明确告知完成时调用                                     |
| `delete_task`   | 删除        | 仅用户明确要求删除时调用，禁止自行清理                              |
| `list_tasks`    | 查询列表      | active/completed/all 三范围；回答待办问题必须以本工具返回为准，不以记忆为准 |

- **硬校验（真兜底）**：时间/内容/分类缺任一拒绝写入并向模型返回中文报错（"缺时间"/"缺内容"/"缺分类"）；"无明确截止时间"不算缺时间
- **分类确认门（真兜底，2026-11-04 增）**：`add_task` 入参含必填布尔 `quadrantConfirmed`——模型提交前先自检"是否已获得用户对分类的明确表态"（卡片点选或文字回答均算）：已获表态才传 `true` 放行；传 `false` 或缺省即拒绝写入，报错"分类未获用户确认"。把"分类必须用户表态"从 prompt 约束升级为程序硬校验
- **写时结算**：任何写操作落地前后对该任务即时结算（见 §8.1）
- **小目标变体**（功能二）：录入入参带归属（父 id），分类继承父级——按归属校验，不算缺分类
- 工具返回给模型的报错与确认文案全部为中文自然语句

## 七、prompt 注入

PromptProvider 常驻注入两块内容：**行为规范**与**当前待办概览**，全部会话模式生效。

### 7.1 行为规范（功能一，十条）

1. 登记三要素缺一不可，任缺其一程序会拒写并报错
2. 时间取值二选一："xx年xx月xx日xx小时xx分钟"（最低到日期）或字面值"无明确截止时间"
3. 四象限分类由"重不重要、急不着急"两个自然维度组成。需要用户表态时优先使用宿主的提问卡片（ask_user），卡片的问题与选项全部用自然口语（如"这场会议对你来说要紧吗？着急吗？"，选项"又要紧又着急 / 要紧但不急 / 着急但不要紧 / 都还好"），禁止把"象限/分类/属性"等插件术语抛给用户，卡片文字上同样禁止。用户点选或文字回答都算明确态度，先听到态度再由模型映射成四词提交；可以建议，态度必须用户给出。add_task 的必答自检项 quadrantConfirmed 为这条兜底：已获表态传 true，尚未表态必须传 false（程序拒写并提示先问），严禁未经询问传 true
4. 用户表述不清或无法确切判断时必须追问，不得代答或猜测
5. 登记入口分流：用户直接要求的直接收集属性；没明确要求的先询问"是否记入待办列表"，同意后才收集；"到点叫我一声"的一次性闹钟需求（无记录/跟进诉求）不登记，引导用户改用宿主定时任务——待办管规划与跟踪，不当闹钟用
6. 删除约束：必须用户明确要求才能删除
7. 数据漂移对齐：列表与记忆对不上时（用户在界面改过是常态），以查询工具返回的最新内容为准
8. 反悔流程：完成态任务说"没做完"时删除旧任务 + 重走新建，内容预填、新时间用户定、分类沿用须用户确认
9. 对话体验：卡片是首选的提问形式，让用户点选而不是手敲字；但卡片上的文字要自然、结合当前对话的上下文，别让用户有填表的感觉——一次问一两个问题，能推断的不再问，禁止罗列全部问题、禁止术语。用户用文字回答与点选同等有效
10. 提醒机制说明：带截止时间的待办临近时自动发系统通知（滑红一次、重要紧急剩 24h 一次；错过开机补发），提醒不经聊天窗口也无需任何授权；用户问"会不会提醒我"照此说明，反映没收到时引导检查系统通知设置与 Cyrene 是否在运行

### 7.2 功能二增补

随功能二实现并入：**流程导向的功能运行说明**（识别提议 → 引导拆解 → 日常运转 → 用户干预四步，见 3.28 第一部分）+ **预判风险节点处置表**（3.28 第二部分）。仅写功能二特有内容，与常驻规范重复的不重复注入。

### 7.3 概览注入

每次注入当前待办概览：未完成条数按四色统计 + 已完成保存条数；具体内容与 id 以 `list_tasks` 查询为准。

## 八、实现口径

### 8.1 结算引擎（三路）

- **写时结算**：登记/修改/完成落地前后对该任务即时结算
- **开机补检**：插件注册时先扫一轮——离线期间跨过滑动/默认完成/提醒时刻的任务在这里补结算；**仍在提醒窗口内**的错过提醒按正常流程补发，已过截止时刻的任务按设计转默认完成、不再补发（§3.15）
- **兜底扫描**：每小时一轮（写时结算与开机补检为主，扫描兜底）
- **判定核心为纯函数**，全部时间规则代码说了算：
  - 滑动：分类为绿/蓝 且 剩余 ≤72h（只有日期按当日 00:00 计）→ 真实改写分类并记录原分类；红/黄为终点；只作用于未完成任务
  - 滑回：截止时间被修改且退出 72h 窗口 → 滑动产生的分类改回原分类，再进窗口按正常规则再滑
  - 默认完成：有截止时间的任务过点仍"未完成" → 自动转（无截止时间永不）
  - 提醒触发：滑红时一次、重要紧急剩 ≤24h 时一次（蓝滑黄静默）；标记以 deadline 字符串判等，改期即新一轮清零
  - 大目标/小目标（功能二）：按 §五 机制资格跳过不适用机制；大目标默认完成按"全部子目标完成 且 已到时限，取较晚时刻"联动结算

### 8.2 提醒通道（自建，不使用宿主定时任务）

不使用宿主定时任务通道的缘由见 §四 #13：授权流程与"跨重启作废"同提醒必须可靠送达根本冲突。自建通道由三部分组成：

- **计时**：插件自管精确定时器——每个提醒时刻（截止前 72h / 前 24h）独立计时；任务数据任何变更即重排全部计时器；超出单一定时器上限（约 24.8 天）的远期时刻不挂精确计时，由兜底扫描覆盖
- **送达 · 核心通道（本机系统通知）**：Electron 原生 Notification——系统级弹窗、进系统通知中心留痕，零授权。插件注册时按分发形态幂等代设 AppUserModelID（宿主自身从不设置；NSIS 安装版用安装器快捷方式背书的 appId，免安装 --dir 目录运行用 exe 完整路径，以卸载器存在性探测区分，Windows 原生通知必需）；点击通知打开工作台窗口；环境不支持通知时记日志跳过
- **送达 · 移动端扩展（QQ NapCat 外发）**：见 3.42——已配置时，提醒触发同时以预写文案经 OneBot HTTP 发送私聊；发送前校验任务状态；未配置时整通道跳过
- **触发即结算**：提醒触发在结算中标记（防重复），事件由两条通道共同消费；开机补检产生的事件照常走两条通道

### 8.3 工程约定

- 构建：esbuild 产插件入口 `index.cjs` + 工作台页面目录 `workbench/`（宿主 manifest 硬约束：入口必须为裸文件名）
- manifest：不声明设置面板（独立窗口是唯一 UI）；不声明定时任务依赖（提醒自建）
- 工作台窗口：无边框自绘标题栏（ipcMain 控制最小化/关闭）；关闭窗口不卸载插件
- 开发期部署：构建产物拷入宿主插件目录，重启宿主生效（§四 #15）
